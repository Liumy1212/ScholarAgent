# AIResearcher 阶段路线图

AIResearcher 的长期目标是形成从论文获取、理解和证据组织，到研究设计、实验与科研写作的
完整闭环。路线图不承诺日期或发布版本；近期阶段写明可验证交付，远期阶段只确定能力方向和
进入条件。

## 状态说明

| 状态 | 含义 |
| --- | --- |
| 已完成 | 已进入当前代码路径，并有相应测试或真实环境验收 |
| 契约已完成 | 机器可读接口已经接受，但消费者实现尚未全部完成 |
| 当前重点 | 下一项需要完成并集成的明确工作 |
| 规划中 | 方向已经确定，尚未进入实现 |

## 阶段 1：本地论文 RAG 基线

阶段 1 建立一条真实可运行的单机闭环。当前 Demo 属于本阶段。

### 1.1 三端应用与契约基线 — 已完成

- React 浏览器客户端、Java BFF 和 Python Agent 可以独立启动。
- 浏览器只通过 Java 访问 Python。
- Agent API、Web API 和 SSE 有机器可读契约及验证脚本。
- 普通 JSON、SSE、PDF 下载和健康检查保持清晰边界。

### 1.2 单 PDF 入库与预览 — 已完成

- Web 通过兼容性接口上传单个文本型 PDF，Python 复用原件登记器保存到原件库并自动入库。
- MySQL 持久化论文、chunk 和带租约的入库任务。
- Worker 使用 PyMuPDF 按页解析、切块、重试并写入索引。
- Web 展示入库状态、失败重试、论文删除和浏览器原生 PDF 预览。
- PDF 代理保留 HTTP Range 语义。

### 1.3 检索、Tool Calling 与引用 — 已完成

- BGE-M3 embedding、Qdrant 召回和本地 reranker 进入真实运行路径。
- `knowledge_base_search` 和 `document_lookup` 作为只读工具提供给模型。
- DeepSeek 使用原生 Tool Calling，自主决定是否调用工具。
- SSE 返回工具状态、正文和终止事件，不输出隐藏推理。
- 引用必须映射到本轮工具证据，并能回溯到论文、页码、quote 和 chunk。

### 1.4 本地论文原件库 — 已完成

目标是把“应用管理的上传文件”升级为用户可长期整理、可扫描、可安全恢复的论文原件库。

已经完成：

- Agent API 与 Web API 已定义原件库信息、持久原件清单、只登记上传、逐篇手动入库、扫描任务、
  扫描项、原件状态和排除/恢复接口。
- Python 已实现 `.private/paper-library`、`originals/`、`.staging/`、安全登记、后台扫描、
  手动入库、SHA-256 复用、排除/恢复和严格检索过滤。
- Java 已代理 library files、manual ingestion、scan、exclusion/restore 与原件 PDF Range，保持
  `Result<T>`、请求 ID、`202` 和 `409 LIBRARY_SCAN_ACTIVE` 语义。
- `.env.example` 与启动脚本已切换到 `AIRESEARCHER_PAPER_LIBRARY_DIR`；`-CheckOnly` 验证
  `.private/` 边界及 Git 忽略规则且不创建目录，旧 storage 迁移步骤已经记录。
- 扫描和原件上传不会自动创建 Paper、入库任务或向量；迁移扫描可按 SHA-256 关联既有 Paper。
- React 已切换到统一原件清单，提供只登记上传、扫描轮询、失败扫描项、逐篇手动入库、重试、
  排除/恢复、分页及原件状态交互，不再提供原件硬删除。
- Chat 只列出 `searchable=true` 的论文。
- `-CheckOnly` 已验证原件库位于受控 `.private/` 边界并被 Git 忽略，且检查前后不会创建目录。
- 已使用合成 PDF 经 Java API 完成放入目录、扫描、`NOT_INGESTED`、手动入库到 `READY`、
  问答检索与页码引用、排除后不可检索、恢复后重新入库、移动保持原件 ID、同路径替换和缺失
  同步；React 页面同时验证了扫描入口、统一清单、禁用状态和 Chat 可检索范围。

完成条件：

- 三端实现与已接受契约一致，旧删除路径不再进入浏览器运行流程。
- 扫描、去重、移动、替换、缺失、排除和恢复均有模块测试。
- Web 上传和目录扫描进入同一原件登记路径，并且都只在用户显式操作后进入同一手动入库路径。
- 启动模板、脚本、架构和部署文档全部使用新配置，模块检查与全栈冒烟均已通过。

#### 论文原件库日常操作修复 — 已完成

已接受的 Agent API 与 Web API 契约新增：

- `GET /library/files` 的可选 `libraryState`，固定为 `ORIGINAL_MISSING`、
  `NOT_INGESTED`、`INGESTED`，服务端必须用同一筛选谓词计算分页项目与 `total`。
- `LibraryInfo.originalsPath`，明确返回扫描器实际递归遍历的 `originals/` 目录。
- 正式的 `DELETE /papers/{paperId}` 知识删除：删除 Paper、任务、chunk 和向量，保留所有
  仍存在的 PDF 原件；同时冻结 `PAPER_BUSY`、依赖失败和 Java 下游错误映射。
- 上传允许 `application/pdf`、`application/octet-stream` 或未提供 MIME，但仍强制
  `.pdf` 文件名、50 MB 上限和 `%PDF-` 签名校验。
- exclusion/restore 继续保留为兼容接口，扫描仍然只登记和同步，不自动入库。

Python Agent 已实现服务端筛选及正确分页、真实 `originalsPath`、宽松上传 MIME、无知识
缺失/替换登记清理，以及不触碰 PDF 的可重试知识删除；相关单元、API、扫描、重复原件和
依赖失败测试已覆盖。Java BFF 已实现枚举校验与原样筛选透传、`originalsPath` DTO、稳定 PDF
part 转发、知识删除 Result 和下游错误映射，且不持久化论文状态。React 页面已实现明确上传
反馈、实际扫描目录、服务端状态筛选、逐行入库/重试/预览与只删除知识流程，并停止把
exclusion/restore 作为页面主删除操作。

两份合成 PDF 的全栈闭环已通过：网页上传会保存到 `originals/uploads/` 并立即显示为未入库；
目录扫描只登记；逐篇入库可到达 `READY`，进入已入库筛选并在 Chat 中检索出带页码引用的
答案；手动移走原件后，扫描会保留 Paper 与向量登记但立即禁止检索；缺失状态删除知识会清理
Paper、任务、chunk、向量和缺失登记；原件仍存在时删除知识会保留 PDF 及其哈希，并将行恢复
为 `NOT_INGESTED`。Contracts、Agent、Backend、Frontend 和仓库差异检查均已通过，测试只使用
仓库外生成的合成 PDF，验收后已清理对应原件与登记。

### 1.5 日常使用加固 — 规划中

目标是让当前闭环可以长期、重复地在本机运行，而不只覆盖成功路径。

- 完善损坏/加密/无文本 PDF、Worker 中断、数据库/向量库/模型不可用和 SSE 中断处理。
- 提供任务、工具调用和请求 ID 的可观测性与问题定位信息。
- 建立不依赖真实私有数据的三端端到端回归。
- 建立可重复 CI、敏感文件门禁和发布检查。
- 验证停止、再次启动、数据库迁移和 named volume 持久化。

完成条件是从空环境首次部署和从既有数据再次启动都能按文档重复完成，自动门禁覆盖主要
失败路径，且不会静默丢失 PDF、论文记录或向量。

## 阶段 2：RAG 工程化与质量提升

阶段 2 是阶段 1 之后的近期详细规划。任何质量改动都需要可重复评测，不能只凭单次主观回答
判断效果。

### 2.1 入库覆盖与文档理解

目标：

- 从“文本型单 PDF”扩展到更真实的论文输入，同时保持原件和证据可追踪。

主要交付：

- 批量入库、队列控制、进度与部分失败恢复。
- 扫描型 PDF OCR，并区分原生文本与 OCR 文本。
- 标题、作者、年份、来源标识等元数据规范化。
- 表格、图片标题、章节结构和参考文献的基础识别。
- 每种解析器和 OCR 结果保留版本、来源页和质量信息。

依赖：

- 阶段 1.4 的统一原件登记与任务边界已经稳定。

完成条件：

- 合成与可再分发样本覆盖原生文本、扫描页、混合页、损坏和加密文件。
- 失败不会产生可检索的半成品，重试不会重复登记或写入向量。
- 所有检索文本都能回溯到原文件、页码和解析方式。

### 2.2 检索与上下文质量

目标：

- 提升不同语言、长问题、术语变化和跨论文查询的召回与最终证据质量。

主要交付：

- 关键词与向量混合检索，并保留各阶段分数和候选来源。
- 查询规范化、拆分或扩展，但不得改变用户原意。
- 可配置 reranker、去重、多样性选择和上下文预算。
- 针对多轮问答的检索问题生成与证据范围快照。
- 引用覆盖、quote 完整性和回答声明—证据一致性检查。

依赖：

- 2.1 提供稳定、可追踪的解析结果；先建立评测基线再替换检索策略。

完成条件：

- 固定评测集可以分别观察召回、排序、上下文和最终引用质量。
- 新策略不会绕过知识库状态过滤或降低证据可追踪性。
- 质量、延迟和资源消耗相对记录的基线可比较。

### 2.3 评测、可观测性与版本管理

目标：

- 让 RAG 质量和运行成本能够持续回归，而不是依赖人工偶发验证。

主要交付：

- 中英文合成评测集、问题类型和期望证据标注。
- ingestion、retrieval、rerank、tool、LLM 和 SSE 分段指标。
- 模型、Prompt、chunk、解析器、collection 和索引版本记录。
- 离线回归报告以及失败样本的可重放输入。
- 延迟、Token、模型调用和本地资源消耗观测。

依赖：

- 评测数据只能使用合成或可再分发材料，不包含私人论文与真实凭据。

完成条件：

- 每项检索或模型策略变化都能与同一基线比较。
- 运行记录足以定位失败发生在解析、召回、排序、工具、模型还是传输阶段。
- 版本变化不会让旧证据失去来源和解释能力。

### 2.4 知识库组织与索引维护

目标：

- 从单默认知识库发展为可以长期维护的论文集合。

主要交付：

- 多知识库、标签、规范化元数据和人工笔记。
- 论文在知识库之间的归属、检索范围与权限边界。
- 单论文重新解析、选择性重建和全库重建。
- 新旧索引版本验证、切换、回退和安全迁移。
- 孤立向量、失败任务和失效原件的可审计清理计划。

依赖：

- 2.3 的版本与回归能力先于大规模索引迁移。

完成条件：

- 用户可以明确选择检索范围，并看到论文与索引状态。
- 重建或迁移失败不会破坏仍可用的旧索引。
- 所有清理操作都有精确范围、预览或人工确认，不隐式删除原件。

## 阶段 3：论文获取与深度阅读

进入条件：阶段 2 已提供可靠入库、可追踪证据和可重复质量评测。

### 3.1 论文发现与受控导入

- 接入 arXiv、公开学术检索或其他用户授权来源。
- 保存来源、查询、获取时间、许可证和原始标识。
- 所有下载复用统一暂存、校验、去重和登记边界。
- 外部连接不得直接写数据库、向量库或解析器内部状态。

### 3.2 结构化深度阅读

- 提取研究问题、方法、数据集、实验设置、结果、限制和作者主张。
- 每一项结构化结论都关联到页码、原文和解析版本。
- 区分论文原文、模型归纳、用户笔记和外部常识。

### 3.3 跨论文综合

- 比较方法、实验条件、指标和结论。
- 识别一致证据、冲突证据、未覆盖条件和研究空白。
- 生成可检查的文献矩阵与证据图，而不是只输出自由文本摘要。

## 阶段 4：研究工作区与创新探索

进入条件：阶段 3 能稳定提供跨论文、可引用的结构化证据。

- 围绕研究问题组织论文、证据、笔记、假设、限制和待办。
- 从证据缺口生成候选研究方向，并明确支持、反对和未知证据。
- 维护研究计划、依赖、决策、人工确认点和长期任务状态。
- 工作流必须可暂停、恢复和审计；是否引入新的编排框架由真实持久执行需求决定。

完成标志是用户能够从一个研究问题得到可检查的文献矩阵、候选创新点和人工确认后的研究
计划，同时保留每项判断的来源。

## 阶段 5：实验闭环

进入条件：研究计划已经能够明确表达假设、证据和人工批准状态。

- 把研究假设转换为实验变量、对照、指标、基线、数据和资源要求。
- 连接代码仓库、数据集与实验运行，但不绕过用户授权或环境安全边界。
- 保存配置、代码版本、输入、日志、结果、失败和负面结果。
- 比较实验结果与论文证据，更新假设状态和后续计划。
- 生成可复现实验包，并能说明哪些步骤仍需人工执行。

## 阶段 6：科研写作与完整闭环

进入条件：论文证据、研究决策和实验结果都具有稳定来源与可复现记录。

- 基于已有证据和实验结果生成提纲、段落和图表计划。
- 对每项声明执行引用映射、来源覆盖和证据强度检查。
- 明确区分原文事实、实验结果、模型归纳和作者观点。
- 支持草稿修订、引用格式、图表资产和可复现附件导出。
- 形成从论文发现、阅读、创新探索、实验到写作的可恢复、可审计闭环。

## 长期约束

- 保持 React -> Java BFF -> Python Agent 的应用边界，除非当前架构文档明确更新。
- Python 继续拥有论文和 AI 领域数据；Java 不复制这些持久化。
- 本地优先和单用户是近期默认，多用户、权限和云部署不是科研闭环的前置条件。
- 远期阶段不提前绑定特定模型、供应商、工作流框架或精确 API。
- 每个阶段只有在依赖能力可验证后才进入实施，路线图状态必须与实际代码同步。
